### 2.2 Поисковые алгоритмы

#### 2.2.1 Полнотекстовый поиск по книгам
**Функция**: `search_books(q: str) -> list[dict]`

**Алгоритм**:
1. Нормализация запроса: `strip()` для удаления пробелов
2. Экранирование специальных символов (`|`, `%`, `_`) в LIKE операциях
3. Создание паттерна поиска: `%{query}%` с ESCAPE='|'

**Многоступенчатый поиск** (в приоритетном порядке):
1. **Поиск в основных полях книги** (LIKE):
   - `title` (название)
   - `author` (автор)
   - `genre` (жанр)
   - Результат помечается как "книга"

2. **Поиск в цитатах** (JOIN + WHERE):
   - Таблица `quotes` JOIN `books`
   - Условие: `quote_text LIKE %pattern%`
   - Результат помечается как "цитата"

3. **Поиск в заметках трекера** (JOIN + WHERE):
   - Таблица `daily_reading` JOIN `books`
   - Условие: `note LIKE %pattern%`
   - Результат помечается как "заметка трекера"

4. **Поиск в тегах** (JOIN + WHERE):
   - Таблица `book_tags` JOIN `books`
   - Условие: `tag LIKE %pattern%`
   - Результат помечается как "тег"

**Дедупликация и сортировка**:
- Используется словарь `found: dict[int, dict]` для дедупликации (ключ — ID книги)
- Для одной книги объединяются типы совпадений (напр., "книга, цитата, тег")
- Финальная сортировка: по названию книги (ASCII-код нижнего регистра), затем по ID

**Экранирование в LIKE**:
```python
_like_contains(q: str) -> str:
    esc = q.replace("|", "||").replace("%", "|%").replace("_", "|_")
    return f"%{esc}%"
```

### 2.3 Статистические алгоритмы

#### 2.3.1 Расчёт прочитанных страниц за период
**Функция**: `sum_daily_between(d0: date, d1: date) -> tuple[int, int]`

```sql
SELECT COALESCE(SUM(pages_read), 0), COALESCE(SUM(minutes_read), 0)
FROM daily_reading 
WHERE read_date BETWEEN %s AND %s
```

**Алгоритм**:
- Суммирование всех записей в таблице `daily_reading`
- В диапазоне дат (включительно с обеих сторон)
- Возвращает кортеж (страницы, минуты)

#### 2.3.2 Разбивка прочитанного по дням
**Функция**: `daily_breakdown_between(d0: date, d1: date) -> list[dict]`

```sql
SELECT read_date, SUM(pages_read) as pages_read, SUM(minutes_read) as minutes_read
FROM daily_reading 
WHERE read_date BETWEEN %s AND %s
GROUP BY read_date 
ORDER BY read_date DESC
```

**Алгоритм**:
- GROUP BY по дате для агрегации нескольких записей в один день
- SUM для каждого дня
- Сортировка по дате в обратном порядке (новые дни первыми)

#### 2.3.3 Подсчёт завершённых книг за период
**Функция**: `count_finished_books_between(d0: date, d1: date) -> int`

```sql
SELECT COUNT(*) FROM books
WHERE reading_status = 'finished'
AND date_finished BETWEEN %s AND %s
```

**Условие**: Считаются только книги со статусом "finished", дата завершения которых попадает в период

#### 2.3.4 Расчёт темпа чтения
**Функция**: `book_pace_estimate(book_id: int, window_days: int = 14) -> dict`

**Алгоритм**:
1. Получение общего количества страниц в книге
2. Суммирование прочитанных страниц (логированных в трекер)
3. Расчёт оставшихся страниц: `remaining = max(0, total - logged)`
4. Выбор записей из трекера за последние N дней (`window_days`)
5. **Расчёт среднего**:
   ```
   pages_in_window = SUM(pages_read) за последние N дней
   days_with_reading = COUNT(DISTINCT read_date) за последние N дней
   avg_pages_per_day = pages_in_window / max(1, days_with_reading)
   ```
6. **Расчёт предполагаемого количества дней до завершения**:
   ```
   est_days = CEILING(remaining_pages / avg_pages_per_day)
   ```
   - Если `remaining_pages` = 0 или `avg_pages_per_day` = 0, то `est_days = None`

**Возвращаемые данные**:
- `title` — название книги
- `page_count` — всего страниц
- `pages_logged` — прочитано (логировано)
- `remaining_pages` — осталось
- `avg_pages_per_active_day` — среднее в день (в дни с чтением)
- `days_with_reading_in_window` — дней с чтением за период
- `estimated_days_to_finish` — предполагаемо дней до конца
- `window_days` — размер временного окна

#### 2.3.5 Подсчёт дней с чтением
**Функция**: `count_reading_days_for_book(book_id: int) -> int`

```sql
SELECT COUNT(DISTINCT read_date) FROM daily_reading WHERE book_id = %s
```

**Алгоритм**: DISTINCT для подсчёта уникальных дней (игнорирует несколько записей в один день)

### 2.4 Алгоритмы прогресса чтения

#### 2.4.1 Расчёт процента прочитанного
**Формула**:
```
progress_percent = (total_pages_logged / total_pages) * 100
progress_bar_value = min(1.0, total_pages_logged / total_pages)
```

**Учитываемые страницы**:
- Из трекера: `total_pages_logged = SUM(pages_read)` из `daily_reading`
- Общее количество: `total_pages = page_count` из таблицы `books`

#### 2.4.2 Визуализация прогресса
- **Progress Bar** (CTkProgressBar): 0.0–1.0 значения
- **Диапазон страниц** (page_start–page_end): Может отличаться от page_count
- **Обновление в реальном времени**: После каждого сохранения записи в трекер

### 2.5 Алгоритмы целей и планов

#### 2.5.1 Цели чтения по периодам
**Таблица**: `reading_goals(scope_year, scope_month, target_pages, target_minutes)`

**Область применения (scope_month)**:
- `0` — цель на весь год
- `1–12` — цель на конкретный месяц

**Алгоритм отслеживания**:
```
target_percentage = count_finished_books / target_books (для месяца/года)
progress_bar = min(1.0, target_percentage)
```

#### 2.5.2 Цели по дням для конкретной книги
**Таблица**: `book_goals(book_id, target_days, deadline_date)`

**Параметры**:
- `target_days` — количество дней до прочтения (макс. 0)
- `deadline_date` — дата дедлайна (опционально)

## 3. Механизмы управления данными

### 3.1 Миграции БД

#### 3.1.1 Автоматические миграции схемы
**Функция**: `ensure_schema()`

**Выполняемые проверки и обновления**:
1. **Добавление колонки `reading_status`** (если не существует):
   - Type: VARCHAR(20)
   - Default: 'planned'

2. **Добавление колонки `page_start`** (если не существует):
   - Type: INT
   - Default: 0

3. **Добавление колонки `page_end`** (если не существует):
   - Type: INT
   - Default: 0

4. **Создание таблицы `book_tags`** (если не существует):
   - Первичный ключ: (book_id, tag)
   - Индекс: idx_book_tags_tag на field `tag`

5. **Создание таблицы `reading_goals`** (если не существует):
   - Первичный ключ: (scope_year, scope_month)
   - Поля: target_pages, target_minutes

6. **Миграция `abandoned` статуса** (`_migrate_abandoned_status`):
   - Расширение VARCHAR для reading_status до 20 символов

7. **Миграция page_number для цитат** (`_migrate_quotes_page_number`):
   - Добавление колонки `page_number` (INT, NULL)

### 3.2 Управление обложками

#### 3.2.1 Сохранение обложки с переименованием
**Функция**: `save_cover_from_path(book_id: int, src_path: str) -> str | None`

**Алгоритм**:
1. Проверка существования исходного файла
2. Валидация расширения (jpg, jpeg, png, gif, webp)
   - Если расширение неподдерживаемо, используется .jpg
3. Генерация нового имени: `{book_id}_{uuid_hex}{ext}`
4. Копирование файла в директорию `COVERS_DIR`
5. Возврат полного пути к новому файлу

**Утилиты**:
- `uuid.uuid4().hex` — генерация уникального идентификатора
- `shutil.copy2()` — копирование с сохранением метаданных

#### 3.2.2 Кэширование изображений
- **Оригинальное изображение**: `_cover_pil_image_original` (PIL Image)
- **Масштабированное изображение**: `_cover_pil_image` (для отображения)
- **CTkImage**: `_cover_photo` (для Tkinter)

### 3.3 Управление тегами

#### 3.3.1 Нормализация тегов
**Функция**: `_norm_tag(s: str) -> str`

**Процесс нормализации**:
1. Приведение к нижнему регистру: `.lower()`
2. Удаление пробелов в начале и конце: `.strip()`
3. Обрезание до 80 символов
4. Возврат пустой строки, если результат пуст

#### 3.3.2 Замена тегов книги
**Функция**: `replace_book_tags(book_id: int, tags: list[str])`

**Алгоритм**:
1. Нормализация каждого тега
2. Удаление дубликатов (используется SET)
3. Удаление всех старых тегов: DELETE FROM book_tags WHERE book_id = %s
4. Вставка новых тегов: INSERT для каждого тега
5. Транзакция завершается COMMIT

## 7. Механизмы работы с БД

### 7.1 Управление подключением

#### 7.1.1 Подключение к MySQL
**Функция**: `connect() -> PooledMySQLConnection | MySQLConnectionAbstract`

**Параметры подключения** (из переменных окружения):
- `DB_HOST`
- `DB_USER`
- `DB_PASSWORD`
- `DB_NAME`
- `DB_PORT`

#### 7.1.2 Использование контекстного менеджера
```python
with connect() as conn:
    cur = conn.cursor(dictionary=True)
    # запросы
    conn.commit()
```

**Преимущества**:
- Автоматическое закрытие подключения
- Защита от утечки соединений

### 7.2 UPSERT операции

#### 7.2.1 Вставка или обновление записи трекера
```sql
INSERT INTO daily_reading (...)
VALUES (...)
ON DUPLICATE KEY UPDATE
page_start = VALUES(page_start),
...
```

**Ключ уникальности**: (book_id, read_date)
**Результат**: Одна запись на день на книгу

#### 7.2.2 Вставка или обновление отзыва
```sql
INSERT INTO reviews (book_id, rating_idea, ...)
VALUES (...)
ON DUPLICATE KEY UPDATE
rating_idea = VALUES(rating_idea),
...
```

**Ключ уникальности**: book_id
**Результат**: Один отзыв на книгу

#### 7.2.3 Вставка или обновление цели чтения
```sql
INSERT INTO reading_goals (scope_year, scope_month, target_pages)
VALUES (...)
ON DUPLICATE KEY UPDATE
target_pages = VALUES(target_pages)
```

**Ключ уникальности**: (scope_year, scope_month)
**Результат**: Одна цель на период

### 7.3 Оптимизация запросов

#### 7.3.1 Индексы
- `idx_book_tags_tag` на таблице `book_tags` для быстрого поиска по тегам
- Первичные ключи на всех таблицах для JOIN операций

#### 7.3.2 Использование COALESCE
```sql
COALESCE(SUM(pages_read), 0) — предотвращение NULL при пустом результате
```

## 12. Анализ сложности алгоритмов

### 12.1 Алгоритм полнотекстового поиска
**Функция**: `search_books(q: str)`

**Сложность**: **O(n + m + k + p)**, где:
- **n** = количество записей в таблице `books`
- **m** = количество записей в таблице `quotes`
- **k** = количество записей в таблице `daily_reading`
- **p** = количество записей в таблице `book_tags`

**Обоснование**:
1. **Поиск по названию/автору/жанру**: O(n)
   - SQL: `SELECT FROM books WHERE title/author/genre LIKE %pattern%`
   - В худшем случае сканируются все n записей
   - **Оптимизация**: Индексы на текстовые поля (если установлены) могут снизить до O(log n)

2. **Поиск по цитатам (JOIN)**: O(m + log n)
   - `SELECT DISTINCT b.id FROM books b JOIN quotes q`
   - Сканирование m цитат + JOIN с таблицей books
   - Primary key используется для JOIN (O(log n) на книгу)

3. **Поиск по заметкам (JOIN)**: O(k + log n)
   - Аналогично цитатам

4. **Поиск по тегам (JOIN)**: O(p + log n)
   - Аналогично цитатам

5. **Дедупликация в памяти**: O(1) за операцию
   - Словарь Python (hash map) обеспечивает O(1) вставку/поиск

**Итоговая сложность**: O(n + m + k + p) последовательно, **но параллельно** за счёт SQL оптимизатора

**Асимптотическое поведение**:
- **Лучший случай**: O(1) — если результат найден в первом запросе и нет совпадений в других
- **Средний случай**: O(max(n, m, k, p))
- **Худший случай**: O(n + m + k + p) — все таблицы просканированы полностью

---

### 12.2 Алгоритм расчёта темпа чтения
**Функция**: `book_pace_estimate(book_id: int, window_days: int = 14)`

**Сложность**: **O(w)**, где w = window_days (обычно 14)

**Обоснование**:
1. **Получение информации о книге**: O(1)
   - Прямой поиск по PRIMARY KEY в таблице `books`

2. **Суммирование прочитанных страниц**: O(r)
   - Требуется один запрос с агрегацией
   - Сложность зависит от количества записей в `daily_reading` для книги

3. **Выборка записей из трекера за период**: O(w)
   - `WHERE read_date BETWEEN d_start AND d_end AND book_id = %s`
   - В худшем случае возвращается до w записей (одна в день за окно)
   - С индексом на (book_id, read_date) это O(log r + w)

4. **Вычисление среднего**: O(w)
   - Итерация по w записям для суммирования страниц

5. **Расчёт дней с чтением**: O(w)
   - Создание множества уникальных дат из w записей

**Итоговая сложность**: O(log r + w), где r — всего записей трекера, w = window_days

**Оптимизация**: 
- Фиксированный размер окна (w = 14) делает алгоритм константой O(1) с практической точки зрения
- **Практическая сложность**: O(1) — на самом деле выполняется за константное время

---

### 12.3 Алгоритм статистики за период
**Функция**: `sum_daily_between(d0: date, d1: date)` и `daily_breakdown_between(d0: date, d1: date)`

**Сложность**: **O(log r + t)**, где:
- **r** = всего записей в `daily_reading`
- **t** = количество записей в диапазоне дат

**Обоснование**:
1. **Поиск с BETWEEN**: O(log r + t)
   - С индексом на `read_date`: B-tree поиск начальной точки O(log r)
   - Затем сканирование t последовательных записей O(t)

2. **Агрегация с GROUP BY**: O(t + g log g), где g = уникальные даты
   - Сканирование t записей
   - GROUP BY требует сортировки (O(g log g)) или hash aggregation (O(g))
   - Обычно MySQL использует hash aggregation для малых g

3. **SUM агрегация**: O(1) за операцию
   - Выполняется в ходе GROUP BY

**Итоговая сложность**: O(log r + t)

**Практическое поведение**:
- Для периода месяц (30-31 день): t ≈ 30-40 записей → практически O(1)
- Для периода год (365 дней): t ≈ 365 записей → всё ещё быстро
- Индекс на `read_date` критичен для производительности

---

### 12.4 Алгоритм подсчёта завершённых книг
**Функция**: `count_finished_books_between(d0: date, d1: date)`

**Сложность**: **O(b)**, где b = количество книг со статусом "finished"

**Обоснование**:
1. **Фильтр по статусу**: O(log b_all)
   - С индексом на `reading_status`: быстрое нахождение стартовой точки
   - b_all = всего записей в `books`

2. **Фильтр по диапазону дат**: O(log b + b)
   - Для каждой книги со статусом "finished" проверяется `date_finished BETWEEN`

**Итоговая сложность**: O(b)

**Оптимизация**:
- При наличии составного индекса (reading_status, date_finished) сложность может быть O(log b_all + b)
- Совместный индекс значительно ускоряет фильтрацию

---

### 12.5 Алгоритм фильтрации по статусу
**Функция**: `list_books_by_status(status: str)`

**Сложность**: **O(log n + b)**, где:
- **n** = всего книг в БД
- **b** = книги с данным статусом

**Обоснование**:
1. **Фильтр WHERE**: O(log n)
   - С индексом на `reading_status`: быстрый поиск
   - Без индекса: O(n) полное сканирование

2. **Сортировка**: O(b log b)
   - `ORDER BY updated_at DESC, id DESC`
   - Требуется сортировка b найденных записей

3. **Возвращение результата**: O(b)
   - Преобразование каждой записи в словарь

**Итоговая сложность**: O(log n + b log b)

**Практическая оптимизация**:
- Если b << n (обычно так), то O(b log b) доминирует
- Для большинства приложений это линейное поведение O(b)

---

### 12.6 Алгоритм поиска по тегам
**Функция**: `list_books_by_tag(tag: str)`

**Сложность**: **O(log p + a + a log a)**, где:
- **p** = всего записей в `book_tags`
- **a** = количество книг с данным тегом

**Обоснование**:
1. **Поиск тега в индексе**: O(log p)
   - `WHERE bt.tag = %s` с индексом idx_book_tags_tag

2. **JOIN с таблицей books**: O(a + log n)
   - Получение a записей из `book_tags`
   - Для каждой: O(log n) поиск в `books` по PRIMARY KEY

3. **Сортировка**: O(a log a)
   - `ORDER BY updated_at DESC, id DESC`

**Итоговая сложность**: O(log p + a log a)

**Оптимизация**:
- Индекс на `book_tags.tag` критичен для быстрого поиска
- JOIN обычно оптимизируется MySQL автоматически

---

### 12.7 Алгоритм нормализации тегов
**Функция**: `_norm_tag(s: str)` и `replace_book_tags(book_id: int, tags: list[str])`

**Сложность**: **O(n + n log n)**, где n = количество тегов

**Обоснование**:
1. **Нормализация каждого тега**: O(1)
   - `.strip()`, `.lower()` — O(L), где L = длина строки
   - L ≤ 80, поэтому O(1) на практике

2. **Удаление дубликатов (SET)**: O(n)
   - Вставка n тегов в SET: O(n) всего

3. **Удаление старых тегов**: O(1)
   - Одно DELETE BY PRIMARY KEY

4. **Вставка новых тегов**: O(n)
   - n INSERT операций

**Итоговая сложность**: O(n)

**Практическое поведение**:
- Типично n ≤ 10 тегов на книгу → O(1) в практике

### 12.8 Алгоритм вывода графиков

### 12.9 Алгоритм экспорта в Excel
**Функция**: `export_statistics_to_excel(output_path: str | Path)`

**Сложность**: **O(b + b×i)**, где:
- **b** = количество книг
- **i** = операции на встраивание одного изображения

**Обоснование**:
1. **Получение списка всех книг**: O(b)
   - `db.list_all_books()`: один запрос, O(b)

2. **Создание Workbook и стили**: O(1)
   - Константные операции

3. **Заполнение ячеек на первом листе**: O(b × 9)
   - 9 ячеек на книгу = O(b)

4. **Загрузка и встраивание обложек**: O(b × i)
   - Для каждой книги: O(i) операции
   - i включает: проверку файла, загрузку, изменение размера, вставку
   - Типично i ≈ 10 операций, O(1)

5. **Создание листа статистики**: O(b)
   - Фильтрация книг по статусу: O(b)
   - Суммирование: O(b)

6. **Сохранение файла**: O(b)
   - Serialization всех ячеек

**Итоговая сложность**: O(b × (1 + i)) ≈ O(b)

**Практическое поведение**:
- Для 1000 книг: ~1-2 сек
- Для 10000 книг: ~10-20 сек
- Операции I/O доминируют над вычислениями

**Практическое поведение**:

### 12.13 Анализ по типам операций

#### SQL-операции
- **Простые SELECT**: O(log n) с индексом, O(n) без
- **WHERE с условиями**: O(log n) начальный поиск, O(k) сканирование k записей
- **JOIN**: O(k × log m) для k записей с индексом на joined поле
- **GROUP BY**: O(k) с hash aggregation, O(k log k) с сортировкой
- **DISTINCT**: O(k) встроенная дедупликация

#### Python-операции
- **Словарь (hash map)**: O(1) вставка/поиск в среднем, O(n) худший случай
- **SET**: O(1) вставка, O(n) пространство для n элементов
- **Сортировка**: O(n log n) Timsort алгоритм в Python
- **Строковые операции**: O(L) где L = длина строки

#### UI-операции
- **Обновление виджета**: O(1) внутри цикла, O(k) для k виджетов
- **Отображение графика**: O(n log n) Matplotlib требует сортировки
